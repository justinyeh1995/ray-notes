Ray Codebase Map

整理自 2026-10-24 · 以 upstream master ce4256ec64 為準 · 相關:Bazel in Ray · Issue 67142 Client Mode Reset

一句話:不用先把 codebase 讀懂。從你呼叫的 public API、traceback 或 log 下手,一次往回追一層。

  • ray.xxx 在哪:打開 python/ray/__init__.py,搜尋那個名字,看它從哪 import。
  • ray xxx CLI 在哪:python/ray/scripts/scripts.py,找 def xxx(。
  • 錯誤在哪:traceback 和 log 都印了檔名和行號,例如 INFO worker.py:1842。
  • 某個函式的行為怪怪的:先看它有沒有掛 @client_mode_hook 之類的 decorator。

1. 怎麼找到程式碼

從 public API 往回追

ray.init、ray.get 這些 ray.* 都是在 python/ray/__init__.py 匯出的:

python/ray/__init__.py:114

from ray._private.worker import (  # noqa: E402,F401
    ...
    init,
    ...
)

所以 ray.init 就是 python/ray/_private/worker.py:1447 的 def init(。

從 CLI 往回追

ray 指令在 python/setup.py:772 註冊:

"console_scripts": [
    "ray=ray.scripts.scripts:main",

所以 ray start 是 python/ray/scripts/scripts.py:801 的 def start(,ray stop 是同檔 1344 行的 def stop(。每個子指令前面都有 @cli.command()。

從 traceback 或 log 往回追

File "python/ray/_private/node.py", line 2272, in _record_stats
    assert ray.experimental.internal_kv._internal_kv_initialized()
AssertionError
2026-10-24 17:18:06,407 INFO worker.py:1842 -- Connecting to existing Ray cluster ...

traceback 由下往上讀,最下面是出錯的那一行,往上是誰呼叫了它。Ray 的 log 格式是 時間 等級 檔名:行號 -- 訊息,行號直接告訴你是哪一行印的。

用 grep 找定義

git grep -n "def _record_stats" -- python
# python/ray/_private/node.py:2270:    def _record_stats(self):

git grep -n "Ray Client is already initialized" -- python
# 從錯誤訊息找到拋錯的地方

git grep 只搜 git 追蹤的檔案,會跳過 bazel-* 那些巨大的 symlink 目錄,比 grep -r 快很多。

2. 三層架構

你的程式 / ray CLI
   │
   ▼
Python API 層       python/ray/             ray.init、@ray.remote、ray.get…
   │
   ▼
Cython 橋接         python/ray/_raylet.pyx   Python ↔ C++,build 出 _raylet.so
   │
   ▼
C++ core           src/ray/                真正執行任務、管理物件

改 Python 層的 .py,editable install 會自動生效。改 _raylet.pyx 或 src/ray/,或是 .proto,要 bazel run //:gen_ray_pkg,見 Bazel in Ray。

4. C++ 端:src/ray/

位置負責什麼
gcs/GCS(Global Control Service)。整個 cluster 的中央服務,記錄 node、actor、job、placement group,也提供 internal KV。一個 cluster 只有一個,在 head node 上。
raylet/raylet。每個 node 一個,在這個 node 上排程任務、管理 worker process 和資源。
core_worker/CoreWorker。每個 driver 或 worker process 裡的 C++ 核心,負責送任務、追蹤物件參考。_raylet.pyx 包的就是它。
object_manager/在 node 之間傳物件,管理 object store(plasma)。
rpc/、*_rpc_client/gRPC server 和 client 的封裝。
protobuf/所有 .proto 定義,Python 和 C++ 共用。
pubsub/、ray_syncer/node 之間同步狀態。
common/、util/共用工具。
design_docs/設計文件。看不懂某個元件時可以先找這裡。

5. 一個 cluster 裡有哪些 process

ray start --head 之後,ray stop 會說停掉了幾個 process。它們大致是:

  • gcs_server(C++,只在 head node):cluster 的中央服務,預設 port 6379。
  • raylet(C++,每個 node):本機排程。
  • dashboard、dashboard agent、log monitor 等 Python process。dashboard 預設在 8265。
  • Ray Client server:ray start --head 預設開在 10001,ray:// 連的就是它。本機 ray.init() 不會開這個。

你的 driver(跑 ray.init() 的那個 Python process)裡面也有一個 CoreWorker。@ray.remote 的 task 和 actor 跑在 raylet 起的 worker process 裡,每個 worker 也各有一個 CoreWorker。

6. 走過一次:issue 67142

ray.init("ray://...")                 _private/worker.py:1697   "://" 分支
  └─ ClientBuilder.connect            client_builder.py
      └─ client_connect.connect       util/client_connect.py
          └─ _ClientContext.connect   util/client/__init__.py:162  開啟旗標
              └─ 連線失敗,旗標沒被關

ray.init()                            _private/worker.py        本機路徑  ← 修在這裡
  └─ Node(...)                        _private/node.py
      └─ _record_stats                node.py:2270
          └─ _internal_kv_initialized()   experimental/internal_kv.py:28  @client_mode_hook
              └─ 被轉到沒連上的 client → False → AssertionError

追的順序:traceback 指到 _record_stats → 看它 assert 的函式 → 發現掛了 @client_mode_hook → 去看 hook 用什麼條件決定轉不轉 → 找到全域旗標 → 找誰開、誰關這個旗標。

深層的 assert 通常只是症狀。先問「它檢查的東西為什麼是錯的」,一路往回追到狀態第一次出錯的地方,再決定是修源頭,還是在最早能察覺的入口擋下來。只修 assert 那一行,錯誤通常會換個地方再冒出來。

7. 容易踩的坑

  • decorator 會改變行為。@client_mode_hook 會在 client mode 時把呼叫轉到 Ray Client,所以函式本體寫的不一定是實際執行的。@PublicAPI、@DeveloperAPI 只是標記 API 的穩定程度。
  • 同名的檔案很多。_private/worker.py(driver/worker)和 util/client/worker.py(Ray Client 的 client 端)完全是兩回事。看 traceback 時要看完整路徑。
  • module 層級的全域變數。像 client_mode_hook.is_client_mode_enabled 這種用 global 改的變數,要透過 module 讀,from ... import 拿到的是快照,見 Issue 67142 第 7 節。
  • Python 和 build 不同步。原始碼是新的,不代表 _raylet.so 和 core/generated/ 也是新的。拉了新 commit 之後出現奇怪的 AttributeError,先懷疑 build。
  • server 和 client 可能在同一個 process。Ray Client 的測試和 helper 會在同一個 process 裡同時跑 server 和 client,靠 disable_client_hook() 區分。在 ray.init 加檢查時要考慮這種情況。
  • IDE 跳到定義時跳到 .pyi。看到函式本體是 ... 不代表它是空的,那只是型別提示檔。真正的實作在 .pyx 或 .pxi,見第 8 節。

8. Cython 與相關副檔名

大部分 issue 只需要 Python。只有 trace 到 ray._raylet 的東西時,才需要看得懂一點 Cython,不用會寫。

副檔名一覽

副檔名是什麼類比Ray 裡的例子
.py一般 Python_private/worker.py
.pyi型別提示檔(type stub),只有簽名,本體都是 ...。給 mypy、pyright、IDE 用,執行時不會被讀_raylet.pyi、includes/object_ref.pyi、includes/unique_ids.pyi(全 repo 只有這 3 個)
.pyxCython 原始碼,會被編譯C++ 的 .cc_raylet.pyx(約 5500 行)
.pxiCython 的 include 檔,用 include "..." 直接貼進 .pyx直接貼進來的程式碼片段includes/object_ref.pxi,在 _raylet.pyx:187 被 include
.pxdCython 的宣告檔,宣告 C++ 的類別和函式,讓 Cython 能呼叫C++ 的 .hincludes/libcoreworker.pxd
.so編譯出來、可以直接 import 的二進位模組(Linux/macOS)_raylet.so
.pyd同上,Windows 版,其實是一個 DLLWindows 上 BUILD 會把 _raylet.so 改名成 _raylet.pyd(BUILD.bazel:268)
 
.pyx + .pxi  ──┐
               ├─ Cython → C++ 編譯器 ─→  _raylet.so(Windows: _raylet.pyd)
.pxd(宣告)  ──┘

.pyi  手寫的,描述 _raylet.so 裡有什麼,給工具看

.pyi 第一行常會寫來源,例如 includes/object_ref.pyi 開頭是 # source: object_ref.pxi。

讀 .pyx 只要認得這幾個

python/ray/_raylet.pyx:3483,CoreWorker.get_objects

    def get_objects(self, object_refs, int64_t timeout_ms=-1):
        cdef:
            c_vector[shared_ptr[CRayObject]] results
            c_vector[CObjectID] c_object_ids = ObjectRefsToVector(object_refs)
        with nogil:
            op_status = CCoreWorkerProcess.GetCoreWorker().Get(
                c_object_ids, timeout_ms, results)
        check_status(op_status)

        return RayObjectsToSerializedRayObjects(results, object_refs)
  • def:一般的函式,Python 可以呼叫。參數可以帶 C 型別,例如 int64_t timeout_ms。
  • cdef:只在 Cython 和 C 裡用的函式或變數,Python 看不到。cdef: 區塊是在宣告 C++ 型別的區域變數。
  • c_vector、shared_ptr:就是 C++ 的 std::vector、std::shared_ptr。
  • C 開頭的名字(CObjectID、CRayObject、CCoreWorkerProcess):C++ 類別,宣告在 includes/*.pxd。
  • with nogil::放開 Python 的 GIL,裡面通常就是呼叫 C++ 的地方。
  • check_status(...):把 C++ 回傳的 Status 轉成 Python 例外。

從 Python 一路追到 C++:以 ray.get 為例

ray.get(ref)
  └─ _private/worker.py:1008       self.core_worker.get_objects(...)
      └─ _raylet.pyx:3483          def get_objects → CCoreWorkerProcess.GetCoreWorker().Get(...)
          └─ includes/libcoreworker.pxd:497
                                   cdef cppclass CCoreWorkerProcess "ray::core::CoreWorkerProcess"
                                   (引號裡是它在 C++ 裡的真正名字)
              └─ src/ray/core_worker/core_worker.h:759
                                   Status Get(const std::vector<ObjectID> &ids, ...)

追到 .pyx 裡呼叫 C++ 的那一行,通常就可以停下來了,只要知道「這裡在呼叫 C++ 的 CoreWorker::Get」。真的要往下看,就去 .pxd 找 cdef extern from "某個.h",知道要去 src/ray/ 的哪個檔案,再找同名的函式。

9. 用 pdb 追 code

想知道程式實際走哪條路時,不要從頭讀到尾,讓 pdb 帶你走。以下指令都在 2026-10-25 實際跑過。

方法一:在分岔點下 breakpoint

conda activate ray-py-3-10
RAY_AUTH_MODE=disabled python -m pdb ~/adhoc/repro_67142_point_2.py

(Pdb) b /home/justinyeh1995_gmail_com/ray/python/ray/_private/worker.py:1871
(Pdb) c

實際輸出

[repro] step 1: failed as expected: ConnectionError: ray client connection timeout
> .../ray/_private/worker.py(1871)init()
-> if bootstrap_address is None:
(Pdb) p bootstrap_address
None
(Pdb) from ray._private import client_mode_hook as h
(Pdb) p h.is_client_mode_enabled
True
(Pdb) w
  .../repro_67142_point_2.py(10)<module>()
-> ray.init()
  .../ray/_private/client_mode_hook.py(134)wrapper()
-> return func(*args, **kwargs)
> .../ray/_private/worker.py(1871)init()
  • step 1(ray://)沒有停在 1871:它在 1697 進了 Ray Client 分支,1735 就 return 了。
  • step 2 停下來了,旗標是 True。
  • w 顯示 ray.init() 先經過 client_mode_hook.py:134 的 wrapper,才進到真正的 init。
  • 那次沒有起 cluster,所以 bootstrap_address 是 None。先 ray start --head 的話它會有值,會走 else。

方法二:post-mortem,直接停在出錯的地方

不用事先知道要停在哪。把要追的呼叫暫時包起來:

import pdb
try:
    ray.init()
except AssertionError:
    pdb.post_mortem()

pdb 會停在 assert 那一行,再用 u 一層一層往上看是誰呼叫的。追「為什麼會走到這裡」時通常最快。

看 @client_mode_hook 怎麼決定

client_mode_hook.py 有三層,每次呼叫時真正執行的是 wrapper:

 86  @overload def client_mode_hook(func)                       ┐ 只給型別檢查用,
 91  @overload def client_mode_hook(*, local_only_kwargs=...)   ┘ 不會執行
 95  def client_mode_hook(func=None, *, local_only_kwargs=()):  ← decorator 本體,import 時跑一次
114      def decorator(func):
118          def wrapper(*args, **kwargs):                      ← 每次呼叫都跑這個
123              if client_mode_should_convert():               ← 旗標 + thread 狀態
126                  if func.__name__ != "init" or is_client_mode_enabled_by_default:
133                      return getattr(ray, func.__name__)(...)  ← 轉給 Ray Client
134              return func(*args, **kwargs)                   ← 不轉,呼叫原函式

breakpoint 下在 95 只會在 import 時停一次。要看每次呼叫怎麼決定,下在 123,並加條件,不然每個掛 hook 的函式都會停:

(Pdb) b /home/justinyeh1995_gmail_com/ray/python/ray/_private/client_mode_hook.py:123, func.__name__ == "_internal_kv_initialized"
(Pdb) c
> .../client_mode_hook.py(123)wrapper()
(Pdb) p func.__name__
'_internal_kv_initialized'
(Pdb) p client_mode_should_convert()
True
(Pdb) n        → 126
(Pdb) n        → 127
(Pdb) n        → 133  return getattr(ray, func.__name__)(...)   被轉給 Ray Client

ray.init 自己在 126 不成立(名字是 init),所以走 134 照常執行;它內部呼叫的 _internal_kv_initialized 在 126 成立,被轉走,回傳 False。

在 Ray 裡用 pdb 的坑

  • breakpoint 用絕對路徑。有兩個 worker.py,而且 editable install 是透過 import hook 對應路徑的,寫 b worker.py:1871 可能找不到或停錯檔案。
  • 行號要對到可執行的那一行。停在註解或空行會得到 *** Blank or comment,breakpoint 不會生效。
  • 不要用 b ray.init 這種函式名稱。ray.init 外面包了 @client_mode_hook,會停在 wrapper,不是 init 本體。
  • q 可能結束不了。pdb 用拋出 BdbQuit 來結束,而它是 Exception 的子類別,會被 script 的 except Exception 接住,script 就繼續跑下去(實測輸出 step 2: local ray.init() failed: BdbQuit)。要強制結束:(Pdb) import os; os._exit(1)。
  • 不要在 ray:// 連線途中停太久。Ray Client 有背景 thread 和 gRPC timeout,停太久恢復後可能出現原本不會發生的 timeout。breakpoint 最好下在連線完成之後。
  • pdb 只停 main thread。Ray Client 的資料串流、log 轉發在別的 thread,停下來時畫面上可能還會冒出 log。
  • 只對 driver 端有效。@ray.remote 的 task 跑在別的 process,要用 ray debug 之類的工具。

LazyVim 可以開 lazyvim.plugins.extras.dap.core,配合 python extra 在 nvim 裡用 debugger,原理一樣,只是有畫面。
