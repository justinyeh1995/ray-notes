Ray · Build · Bazel

Bazel in Ray

整理自 2026-10-24 · 以 upstream master ce4256ec64 為準 · Bazel 7.5.0(透過 Bazelisk) · 相關:Issue 67142 Client Mode Reset

一句話:Bazel 把 repo 切成很多 package(有 BUILD.bazel 的目錄),每個 package 裡宣告一堆 target,用 //路徑:名字 指名。你下的每個 bazel build/run/test 指令,都是在說「幫我把這個 target 和它依賴的東西弄到最新」。

  • 平常寫 Python:pip install -e . 之後改 .py 不用 build。
  • 拉了新 commit,或改了 .proto/.cc/.h/.pyx:bazel run //:gen_ray_pkg。
  • 跑測試:日常用 pytest;想照 CI 的方式跑才用 bazel test //python/ray/tests:test_xxx。

1. 心智模型:五個名詞

名詞是什麼Ray 裡的例子
workspace整個 repo 的根,有 WORKSPACE 檔。名字在 gen_extract.py 裡寫死成 io_ray。~/ray/
package任何有 BUILD.bazel 的目錄。它管到下一個有 BUILD 的子目錄為止。python/ray/tests、src/ray/protobuf
targetBUILD 裡的一個 name = "..."。可以是 library、binary、test、檔案群組。test_client_init、gen_ray_pkg
labeltarget 的全名://package:name。同 package 內可以省成 :name。//python/ray/tests:test_client_init、//:gen_ray_pkg
rule / macro產生 target 的函式。rule 是 Bazel 內建或外部載入的;macro 是 .bzl 裡用 Starlark(長得像 Python)寫的包裝。py_test(rule)、py_test_module_list(macro)

// 代表 workspace 根目錄,所以 //:gen_ray_pkg 就是「根目錄那個 BUILD.bazel 裡叫 gen_ray_pkg 的 target」。

Label 的萬用寫法://python/ray/tests:all 是該 package 的所有 target,//python/ray/tests/... 是該目錄底下所有 package 的所有 target。

2. 設定檔怎麼讀

.bazelversion:要用哪個 Bazel

內容只有一行 7.5.0。你裝的 bazel 其實是 Bazelisk(v1.29.0),它會讀這個檔,自動下載並執行對應版本。所以不用自己管 Bazel 版本。

WORKSPACE:外部依賴

宣告 grpc、protobuf、rules_python 這些外部套件從哪裡下載。BUILD.bazel 第一段 load("@rules_python//python:defs.bzl", ...) 裡的 @rules_python 就是在這裡定義的外部 repo。@名字 開頭的 label 一律指外部 repo。

Bazel 新版改用 MODULE.bazel(bzlmod),但 Ray 還沒換。.bazelrc 開頭的 common --noenable_bzlmod 就是在關掉它。

.bazelrc:預設 flag

每一行的格式是 指令[:config名] --flag:

build --compilation_mode=opt        # 所有 build 都帶這個 flag
test  --test_env=LC_ALL             # 所有 test 都帶
build:debug -c dbg                  # 只有加了 --config=debug 才帶
build:linux --cxxopt="-std=c++17"   # 平台 config,見下面
  • 沒有冒號的行每次都生效。所以 Ray 預設就是 -c opt(最佳化 build)。
  • build:xxx 是一組具名設定,要用 --config=xxx 才會套用。Ray 定義了 debug、asan、tsan、ci 等。例如 bazel build --config=debug //:ray_pkg。
  • build:linux/build:macos 比較特別:因為有 build --enable_platform_specific_config,Bazel 會依照你的作業系統自動套用。在 Linux 上不用加 --config=linux。
  • common 套用到所有指令(build、test、run、query…)。test 會繼承 build 的設定。

個人設定放這裡(.bazelrc:278)

try-import %workspace%/.user.bazelrc

在 repo 根目錄建一個 .user.bazelrc(不會被 commit),就能加自己的 flag,不用改共用的 .bazelrc。也可以放在 ~/.bazelrc。你目前兩個都沒有。機器記憶體不夠時,/rebuild skill 建議加:

build --local_ram_resources=HOST_RAM*.5 --local_cpu_resources=4
build --disk_cache=~/bazel-cache

3. 四個指令

指令做什麼例子
bazel build產出 target 的檔案,放進 bazel-bin/。不會動到你的 source tree。bazel build //src/ray/raylet:raylet
bazel run先 build,再執行那個 binary。執行時會設 BUILD_WORKSPACE_DIRECTORY,所以程式可以寫回 repo。bazel run //:gen_ray_pkg
bazel testbuild 並執行 test target,結果在 bazel-testlogs/。bazel test //python/ray/tests:test_client_init
bazel query查 target 之間的關係,不 build 任何東西。見第 6 節

為什麼 rebuild 用 run 不用 build?

bazel build 只把結果放在 bazel-bin/(Bazel 自己的 cache 目錄),你的 python/ray/ 不會變。gen_ray_pkg 是一個 Python 程式,bazel run 執行它時,它會把 build 好的 zip 解壓回 python/ray/(見第 4 節)。所以只有 run 才會更新你 editable install 實際 import 到的檔案。

Another command is running. Waiting for it to complete...

每個 workspace 只有一個 Bazel server,一次只能跑一個指令。你在一個終端機 build 時,另一個終端機的 bazel 指令(連 bazel version 都一樣)會排隊等。不是當掉了。

repo 根目錄的 bazel-* symlink

  • bazel-bin → build 產出(~/.cache/bazel/.../bazel-out/k8-opt/bin,k8-opt = x86_64 Linux + opt 模式)
  • bazel-out → 所有模式的產出
  • bazel-testlogs → bazel test 的 log
  • bazel-ray → execroot,Bazel 實際執行 action 的地方

這些都是 cache,可以整個刪掉。bazel clean 會清掉產出;bazel clean --expunge 連下載的外部依賴都清,下次 build 會很久。

4. 讀根目錄的 BUILD.bazel:gen_ray_pkg 做了什麼

從你最常跑的那個 target 往回追,就能看懂大部分的根 BUILD。

BUILD.bazel:465

py_binary(
    name = "gen_ray_pkg",
    srcs = ["gen_ray_pkg.py"],
    data = [
        ":ray_pkg_zip",       # C++ binary:raylet、gcs_server、_raylet.so
        ":ray_py_proto_zip",  # 產生出來的 *_pb2.py
    ],
    deps = ["//bazel:gen_extract"],
)
  • srcs:這個程式自己的原始碼。
  • data:執行時需要的檔案。Bazel 會先把它們 build 好,放進 runfiles 讓程式讀得到。
  • deps:它 import 的其他 library。

gen_ray_pkg.py 很短:清掉 python/ray/core/generated 和 python/ray/serve/generated,再把這兩個 zip 解壓到 python/。

往回追 protobuf 那條線

src/ray/protobuf/common.proto
  └─ //src/ray/protobuf:common_proto        proto_library      (protobuf/BUILD.bazel:9)
      └─ //src/ray/protobuf:core_py_proto   python_grpc_compile (protobuf/BUILD.bazel:517)
          └─ //:core_py_proto_files         pkg_files,前綴 ray/core/generated
              └─ //:core_py_proto_zip       pkg_zip
                  └─ //:ray_py_proto_zip    genrule,用 sed 修 import 路徑
                      └─ //:gen_ray_pkg     py_binary,解壓到 python/

Bazel 依照這條依賴鏈判斷要重做什麼。common.proto 一改,整條線都會重跑;沒改到的部分直接用 cache。

2026-10-24 踩到的坑:ray#65487 在 common.proto 加了 disable_job_level_lineage_reconstruction,但上次跑 gen_ray_pkg 是在那之前。Python 原始碼已經會讀這個 field,python/ray/core/generated/common_pb2.py 卻還是舊的,所以每個 ray:// 連線都在 server 端拋 AttributeError。editable install 只會自動更新 .py 原始碼,不會更新 Bazel 產生的檔案。

只想更新 protobuf,不想重編 C++?

根 BUILD 裡還有一個 //:gen_py_proto(BUILD.bazel:453)。它只解壓 ray_py_proto.zip,比 gen_ray_pkg 快很多。但如果同一批 commit 也改了 C++,_raylet.so 還是舊的,所以拉了一大批 commit 之後,保險的做法還是 gen_ray_pkg。

BUILD 裡其他常見的 rule

  • filegroup:幫一群檔案取個名字,本身不做事。
  • alias:另一個 target 的別名。搭配 select({...}) 可以依平台指到不同 target,例如 redis-server。
  • genrule:跑一段 shell(cmd),由 srcs 產出 outs。$(location :x) 會換成 :x 的實際路徑。
  • select():依照 config 選值。"//conditions:default" 是 fallback。

5. 讀 python/ray/tests/BUILD.bazel

conftest:為什麼 fixture 不用 import

py_library(
    name = "conftest",
    srcs = glob(["**/conftest.py"]),
    visibility = ["//python/ray/tests:__subpackages__", ...],
)

把所有 conftest.py 包成一個 library,每個測試的 deps 都會列 ":conftest"。pytest 會自動載入 conftest 裡的 fixture(例如 shutdown_only),但 Bazel 只會把 deps/data 宣告過的檔案放進測試的 runfiles,也只看它們決定 cache 要不要失效,所以要明確宣告。

visibility 控制誰能依賴這個 target。__pkg__ 是只有那個 package,__subpackages__ 是那個 package 加上所有子目錄。Ray 的規矩是能多私有就多私有,細節見 bazel-visibility skill。

py_test_module_list:一個檔案一個 test target

python/ray/tests/BUILD.bazel:156

py_test_module_list(
    size = "medium",
    files = [
        "test_client_builder.py",
        "test_client_multi.py",
        ...
    ],
    tags = ["custom_setup", "exclusive", "ray_client", "team:core"],
    deps = [":conftest", "//:ray_lib"],
)

這不是 Bazel 內建的 rule,而是 bazel/python.bzl:73 定義的 macro,檔案開頭用 load("//bazel:python.bzl", "py_test_module_list") 載入。它做的事很簡單:

def py_test_module_list(files, size, deps, extra_srcs=[], name_suffix="", **kwargs):
    for file in files:
        name = paths.split_extension(file)[0] + name_suffix   # 去掉 .py
        native.py_test(
            name = name,
            main = file,
            srcs = extra_srcs + [file],
            deps = deps,
            size = size,
            **kwargs                                          # tags、env 等原樣傳下去
        )

所以 test_client_multi.py 會變成 target //python/ray/tests:test_client_multi,同一個 list 裡的檔案共用 size、tags、deps。

那 Bazel 怎麼跑 pytest?

main = file 代表 Bazel 是直接 python test_client_multi.py,不是呼叫 pytest。這就是為什麼 Ray 每個測試檔最後都有:

if __name__ == "__main__":
    sys.exit(pytest.main(["-sv", __file__]))

少了這段,Bazel 執行那個檔案時什麼都不會跑,測試卻會顯示通過。

參數的意思

參數意思
sizesmall/medium/large/enormous,決定預設 timeout(60s/300s/900s/3600s)。CI 也用它分組。
tags = ["exclusive"]Bazel 內建意義:這個測試不跟其他測試並行。會起 cluster 或動到全域狀態的測試要加。
tags = ["team:core"]Ray 自己的慣例:哪個團隊負責。
tags = ["ray_client"]Ray 自己的分組標籤,CI 用 bazel query 依 tag 挑測試(見第 6 節)。
tags = ["custom_setup"]Ray CI 用來標記需要特別環境的測試。
env = {...}測試的環境變數。例如有一組設 RAY_CLIENT_MODE=1,讓整批測試都走 client mode。
deps = ["//:ray_lib"]根 BUILD 的註解說它是 dummy:把 python/ray/**/*.py 都列進來,任何 Ray 原始碼一改,這些測試的 cache 就失效,會重跑。

什麼時候要改 BUILD?

  • 在現有測試檔裡加測試函式:不用。target 是以檔案為單位,新函式自動包含在內。這次 issue 67142 在 test_client_multi.py 加的測試就是這種。
  • 新增測試檔:要。把檔名加進適合的 py_test_module_list 的 files,不然 CI 根本不會跑它。挑 size 和 tags 跟它最像的那一組。
  • 新增 .cc/.h:要。加進對應的 ray_cc_library 的 srcs/hdrs。

6. bazel query:查不知道的事

# 某個檔案屬於哪個 test target?
bazel query 'attr(main, test_client_multi.py, //python/ray/tests:*)'

# tests 目錄有哪些 py_test?
bazel query 'kind(py_test, //python/ray/tests:*)'

# 有某個 tag 的測試(macOS CI 實際在用,ci/ray_ci/macos/macos_ci.sh:54)
bazel query 'attr(tags, "ray_client", tests(//python/ray/tests/...))'

# 這個 target 依賴什麼?
bazel query 'deps(//:gen_ray_pkg, 2)'

# 誰依賴 common_proto?(改 proto 前想知道影響範圍)
bazel query 'rdeps(//..., //src/ray/protobuf:common_proto, 1)'

# 看 macro 展開後的真正 target 長怎樣
bazel query --output=build //python/ray/tests:test_client_multi

最後一個最有用:它會印出 py_test_module_list 展開後的 py_test(...),包含實際的 name、srcs、tags。看不懂某個 macro 時,用它看結果最快。

注意:query 也要 Bazel server,build 在跑的時候會排隊。

7. pytest 還是 bazel test?

pytest path::testbazel test //...:target
粒度可以只跑一個函式以檔案為單位。Ray 的測試檔用 pytest.main(["-sv", __file__]),不讀 sys.argv,所以 --test_arg=-k 傳不進去,沒辦法只跑一個函式
環境你的 conda env、你的 working treesandbox,只看得到 deps/data 宣告的東西,套用 BUILD 的 env 和 tags
timeoutpytest.ini 的 180s依 size
適合開發時反覆跑確認 CI 會怎麼跑、BUILD 有沒有寫對

兩種都要先把 build 弄到最新。pytest 不會幫你 rebuild,bazel test 也只 build 測試宣告的依賴,而 //:ray_lib 只是 .py 檔,不會觸發重編 _raylet.so。

8. 速查

# 拉了新 commit 之後(最常用)
bazel run //:gen_ray_pkg

# 只有 proto 變了
bazel run //:gen_py_proto

# debug build(要用 gdb 時)
bazel run --config=debug //:gen_ray_pkg

# 只 build 一個 C++ binary
bazel build //src/ray/gcs:gcs_server

# 跑一個測試檔,照 CI 的方式
bazel test //python/ray/tests:test_client_multi --test_output=errors

# 看某個 target 的完整定義
bazel query --output=build //python/ray/tests:test_client_multi
