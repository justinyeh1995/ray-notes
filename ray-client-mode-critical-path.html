Ray Client 模式:關鍵路徑與設計沿革

整理自 2026-10-20~21 · 分支 fix/ray-init-client-mode · 行號以 master 95d3a43269 加上未 commit 的修改為準 · 延伸自 Issue 67142 Client Mode Reset · ray#67142

一句話:client mode 存在的目的只有一個 —— 讓你不用改任何一行 Ray 程式碼,就能在自己筆電的 Python shell 裡驅動一個遠端 cluster。為了達成這件事,它用了一個 process-wide 的旗標 is_client_mode_enabled 加呼叫時 dispatch,讓所有 @client_mode_hook 修飾的函式改走 Ray Client 路徑。這條鏈上有兩處會打開旗標、三處會關閉旗標,而「打開」和「關閉」的條件並不對稱。

  • 第 1 節是「client mode 是為了什麼」;第 6 節是「它為什麼長成這樣」(設計沿革 + 病史)。
  • 這次修改加在鏈的第 7 層(_ClientContext.connect 的 except),而那一層看不到「別的 context 是否還連著」。
  • 實測結果:修好了 issue 的 repro,但在 allow_multiple 與 _inside_client_test 兩條路徑上造成新的回歸。資料見第 8 節。
  • 建議:改在第 6 層(RayAPIStub.connect)處理,比照既有的 disconnect / shutdown,只在沒有任何 context 存活時才關。

1. Client mode 是為了什麼

目的其實只有一句話:

讓你不用改任何一行 Ray 程式碼,就能在自己筆電的 Python shell 裡,驅動一個遠端的 cluster。

架構上,你筆電上那個 process 不是 cluster 的成員。client server 幫你在 cluster 裡起了一個真的 driver,你的 ray.get / @ray.remote 全部走 gRPC 送過去。

為什麼需要它(2020 年那個時空)

那時候 Ray 只能「把 script 丟到 cluster 上跑」,你沒辦法在自己筆電的 REPL 裡面對一個遠端 cluster 逐步除錯。Client mode 補的就是這個洞。它跟 Jobs API 是同一時期的兩條路,定位不同:

方式定位driver 在哪
ray.init()本機開發你的筆電(而且是本機 cluster)
ray.init("ray://…")互動式開發遠端 cluster你的筆電,但只是 gRPC proxy;真的 driver 在 cluster 裡
Jobs API生產 / ML workloads(現在的主流)cluster 裡,完全不需要你的筆電

今天誰還在用

  • ray.util.state 的 State API 可以直接吃 ray:// address,從筆電查遠端 cluster 狀態(util/state/api.py:127)
  • Spark on Ray 就是走 ray:// 連的(util/spark/cluster_init.py:1227)
  • Dask on Ray 有 client mode 的測試路徑
  • ray.util.client 本身是 public API

代價(為什麼 ML workloads 不推薦)

  • 物件全部要經過 client server 序列化再傳,沒有本機 object store 的 zero-copy → 慢
  • 連線斷掉超過 30 秒,workload 直接被殺(DEFAULT_CLIENT_RECONNECT_GRACE_PERIOD = 30,ray_constants.py:339)
  • doc 直接講:"Ray Client has architectural limitations and may not work as expected when using Ray for ML workloads (like Ray Tune or Ray Train). Use Ray Jobs API."

3. ray:// 到底是什麼

一句話:ray:// 不是 wire protocol,是 URL scheme。而且這個 scheme 的「handler」是用 importlib.import_module() 動態 import 出來的 Python module。

各種 address 形式的差別

寫法實際上在做什麼driver 是誰
ray.init()起一個 local clusterC++ core worker(就本機)
ray.init("auto")attach 到既有 cluster 的 GCSC++ core worker(本機,只是接遠端 GCS)
ray.init("1.2.3.4:6379")同上,直接給 GCS addressC++ core worker
ray.init("ray://1.2.3.4:10001")走 gRPC 到 client server這個 python process 本身不是 core worker
ray.init("http://…")直接被擋下client_builder.py:353-362 明確報錯(可能是 RAY_ADDRESS 設成 API server)

RAY_ADDRESS=ray://head:10001 也會進 client mode —— worker.py:1686-1694 會用 env var 覆蓋 address。

為什麼這跟 flag 洩漏有關:ray:// 是開啟 client mode 的唯一入口。worker.py:1696 那個 "://" in address 的判斷就是分岔點,分岔之後旗標才會被打開。所以「ray:// 是什麼」跟「client mode 為什麼會壞掉」是同一條線的兩端。

5. 分派決策

每個被 @client_mode_hook 修飾的函式,在被呼叫時都會問一次這個問題。

走 Ray Client 走本機

為什麼這重要:旗標壞掉時,ray.get / ray.put / @ray.remote 全部會改走本機路徑。旗標「卡在 True」時則相反:本機的 ray.init() 起來了,但所有操作都被轉去一個根本沒連上的 client。

6. client mode 為什麼長成這樣

要理解 flag 為什麼是 global、為什麼關不掉,得先知道它原本要解決什麼。原始設計出處是 PR #13031(barakmich, 2020-12),說明寫得很清楚:

RAY_CLIENT_MODE=1 python <everyday ray file>

To wit, RAY_CLIENT_MODE=1 python ray/tune/examples/pbt_example.py works unmodified.

"This finally allows exposure of the experimental ray client without
modifying (much) ray code."

唯一的設計約束:使用者跟第三方 library 寫的每一行 Ray 程式碼都不該需要改。其他一切都從這裡推導出來。

為什麼是 decorator、而且分派在「呼叫時」

最直覺的做法是到處塞 if is_client_mode(): return client_impl(...) —— 那要動到大量 Ray 內部程式碼,正好是 #13031 想避免的。所以做法變成把真實的 ray module 的公開函式包一層:

def client_mode_hook(func):
    def wrapper(*args, **kwargs):
        if client_mode_enabled and _client_hook_enabled:
            return getattr(ray, func.__name__)(*args, **kwargs)   # client 版的同名函式
        return func(*args, **kwargs)
    return wrapper

分派靠 func.__name__ 對應到 client stub 的同名 method —— 這就是為什麼 ray/util/client/__init__.py 要做一個形狀模仿 ray module 的 RayAPIStub。

為什麼這個開關「必須」是 process-wide 的

關鍵是時間軸:import ray 和 @ray.remote 發生在 module import 時,遠早於 ray.init("ray://...");library 更可能在 import 期就宣告好 remote function。所以轉換被延遲到提交任務時才發生(remote_function.py:369):

if client_mode_should_convert():
    return client_mode_convert_function(self, args, kwargs, **task_options)

client_mode_hook.py:192-196 的註解講得很直白:

python/ray/_private/client_mode_hook.py

The common case is to transparently convert that RemoteFunction
to a ClientRemoteFunction. This happens in circumstances where a
RemoteFunction is declared early, in a library and only then is Ray used
in client mode -- necessitating a conversion.

轉換結果還會 cache 在 function class 上(RAY_CLIENT_MODE_ATTR),並用 _converted_key_exists 對當前 session 驗證,因為同一個 interpreter 裡可能跨 client session 重用同一個 func_cls。

為什麼不能是 thread-local 或 contextvar? 因為決策必須對整個 process 一致:library 裡宣告的 @ray.remote function、還沒 ray.init() 就存在的 actor class,都得一起變 client 版。宣告當下根本沒有「現在是哪個 client」的概念 —— 只有「這是什麼 mode」。

三層狀態

狀態範圍誰在動
is_client_mode_enabledprocessray.init("ray://…")、ray.client().connect()
_client_hook_status_on_threadthreaddisable_client_hook(),給 client server 端用(server 要用真的 Ray API)
is_client_mode_enabled_by_defaultprocessRAY_CLIENT_MODE=1,跑整個 test suite 用

#16731 做的事就是把「hook status」從 global 改成 thread-local(global 太粗),但mode 本身維持 global。

結構性債與它的歷史

mode 是 process-wide(1 個 flag),但連線是 per-context 的。allow_multiple=True 之後可以同時有好幾個 _ClientContext,各自一條 gRPC channel。一個 flag 沒辦法表達「我現在該對哪一條連線講話」—— 設計上直接推給 client stub 自己在呼叫時解析(RayAPIStub._cxt.handler)。

這個 punt 就是所有同類 bug 的溫床:

時間PR事件
2020-12#13031起源:把 decorator 塞進真的 ray module
2021-02#13639「declared early」的轉換機制(現在的 client_mode_convert_function)
2021-04#15257"Don't leak a global enabling of client mode" —— 同一個病的第一個實例
2021-06#16731hook status 改成 per-thread
2021-08#17942allow_multiple:多個 context,還是一個 flag
2026-10#67142connect 失敗後 flag 卡住;而要關它時沒有任何 ownership 規則

「關的那一側」從來沒被設計過。整個 codebase 裡最接近 ownership rule 的就是 RayAPIStub.disconnect():

if len(_all_contexts) == 0:
    _explicitly_disable_client_mode()

也就是「沒有任何 context 活著才關掉 mode」。而 _ClientContext 這層看不到 _all_contexts —— 它只知道自己的 worker。這正是為什麼「在哪裡關」比「要不要關」更關鍵。

如果要重新設計,方向是什麼

不是去修「_explicitly_disable_client_mode() 該不該呼叫」,而是把「mode」從 process-wide boolean 收進 context 裡 —— RayAPIStub 已經有 thread-local 的 context 了。把「這條連線是 client」變成連線自己的性質,而不是整個 process 的性質,這樣 allow_multiple、失敗重連、測試 harness 三種情境就自然分開了。

現在它們全部擠在同一個 boolean 上 —— 這才是同一個病反覆長出來的原因。

不過這是架構層級的改動,遠超 good-first-issue 的範圍。#67142 能做的還是先修好那個 flag 的生命週期。

9. 建議的改法

把 __init__.py:222 拿掉,改在 RayAPIStub.connect 處理,條件比照既有的 disconnect / shutdown。

python/ray/util/client/__init__.py · RayAPIStub.connect

def connect(self, *args, **kw_args):
    self.get_context()._inside_client_test = self._inside_client_test
    try:
        conn = self.get_context().connect(*args, **kw_args)
    except Exception:
        global _lock, _all_contexts
        with _lock:
            # 失敗的 context 從來沒被加進 _all_contexts,
            # 所以 len == 0 代表「這次失敗前也沒有任何連線」
            if not self._inside_client_test and len(_all_contexts) == 0:
                _explicitly_disable_client_mode()
        raise
    global _lock, _all_contexts
    with _lock:
        _all_contexts.add(self._cxt.handler)
    return conn

這一層同時滿足三件事:看得到 _all_contexts、看得到 _inside_client_test、而且失敗的 context 根本還沒被登記進去,所以 len == 0 正好就是「可以安全關旗標」的條件。

副作用:_ClientContext.init(__init__.py:299)內部直接呼叫 self.connect,不經過 RayAPIStub.connect,那條路徑不會被這個保護涵蓋。RayAPIStub.init(__init__.py:385)可以加同樣的保護,看要不要一起做。

但 issue 已經改寫了,上面的方向可能不對。2026-10-20 23:17 issue 作者把標題從「A failed ray:// connect leaves Ray Client mode on, breaking a later local ray.init()」改成「After a failed ray:// connect, ray.init() raises a bare AssertionError and an allow_multiple=True retry times out」,body 也重寫,新增了一個 Explicit 的 Expected:

  1. A local ray.init() still fails, but with an error that says Ray Client is already initialized. instead of a bare AssertionError.
  2. ray.init("ray://<live address>", allow_multiple=True) connects.

也就是說 issue 現在要的是旗標保持開著(否則 local init 會直接成功而不是「失敗但訊息清楚」),而是要讓錯誤訊息變清楚。這跟「connect 失敗就清掉旗標」是相反的方向。

而 "Ray Client is already initialized." 這句話在 master 上不存在 —— 它只出現在 PR #67126(同一個作者)把 util/client_connect.py:47 的 "Ray Client is already connected." 改寫而來。所以 Expected #1 需要新寫程式碼,不是清旗標。

Expected #2(allow_multiple timeout)則跟這次修改無關;issue 作者說他沒找出根因,懷疑是 #67126 造成的(#67126 有動到 util/client/worker.py 與 util/client_connect.py),而且他沒在純 master 上重現過。

值得先問作者的問題:「local ray.init() 應該失敗」真的是對的嗎?從使用者角度,「client 連線失敗了,換成本機跑」是很合理的需求,現在卻拿到一個無言的 AssertionError。如果改成「本機 ray.init() 成功,而且 client mode 乾淨地關掉」,其實比 issue 描述的期望更好 —— 現行的一行修改正好就是這樣。
