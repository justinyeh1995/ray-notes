Issue 67142 Client Mode Reset

整理自 2026-10-18 的 review · 分支 fix/ray-init-client-mode · 行號以 master 95d3a43269 加上未 commit 的修改為準 · ray#67142 · 關鍵路徑圖見 Ray Client 模式關鍵路徑

  • 問題 B:開啟有 _inside_client_test 判斷,關閉卻沒有,兩邊不對稱。
  • 建議:改在 RayAPIStub.connect 處理,比照 disconnect,只在 len(_all_contexts) == 0 且不在 client test 時才關。
  • 驗證狀態:已驗證。2026-10-20 用 stub harness 跑過修改前後,結果見 Ray Client 模式關鍵路徑 第 5 節:issue 的 repro 修好了,但 allow_multiple 與 _inside_client_test 兩條路徑出現回歸。end-to-end 仍需在有 C++ build 的環境確認。

2026-10-24 更新:issue 已改版,第 1 到 6 節依據的是舊版。作者跟 Rueian 討論後改了 title 和預期行為:失敗後的本機 ray.init() 要繼續失敗,但改成拋 Ray Client is already initialized.,而不是重設旗標讓它成功。第 5 節的修法因此不再適用。新的範圍和 #2 的來源見第 8 節。

1. Issue 在講什麼

症狀是什麼?

ray.init("ray://...") 連線失敗之後,同一個 process 再呼叫本機的 ray.init() 會在 node.py 的 _record_stats 撞到 AssertionError,而不是正常啟動本機 cluster。

issue 附的 repro

import ray
import ray._private.client_mode_hook as hook
from ray._common.network_utils import find_free_port

try:
    # 這個 port 沒有任何東西在 listen
    ray.init(f"ray://127.0.0.1:{find_free_port()}")
except ConnectionError as e:
    print("ray:// connect failed:", type(e).__name__, e)
print("client mode enabled after failure:", hook.is_client_mode_enabled)  # True
ray.init()  # AssertionError

根因?

client_mode_hook.is_client_mode_enabled(client_mode_hook.py:16)是 module-level 的全域旗標,決定所有 @client_mode_hook 修飾的函式要走本機路徑還是 Ray Client 路徑。_ClientContext.connect 在連線之前就把它打開(__init__.py:162),失敗時只呼叫 per-context 的 self.disconnect(),而這個 disconnect 不會動到旗標。旗標就這樣一直停在 True。

Workaround:失敗後手動呼叫 ray.util.disconnect(),它走的是 RayAPIStub.disconnect,會把旗標關掉。

為什麼旗標開著,ray.init() 就會撞 AssertionError?

一句話:init 走本機,init 裡的檢查卻跑去問一個不存在的 client。(2026-10-31 整理)

  1. ray.init 雖然掛了 @client_mode_hook,但 hook 對 init 有特例(client_mode_hook.py:126),只有 RAY_CLIENT_MODE=1 才轉送。所以 init 本體照常走本機路徑。
  2. init 裡面呼叫的其他函式沒有這個特例。node.py:2279-2281 的 _record_stats 先寫入 internal_kv,再 assert 它已經初始化。
  3. 寫和讀走了不同的路:
函式(internal_kv.py)@client_mode_hook旗標開著時實際執行
_initialize_internal_kv(寫)沒有(:20)本機版本,設定本機的 global_gcs_client
_internal_kv_initialized(讀)有(:28)轉給 client。client 沒連上,_ClientContext.__getattr__(__init__.py:273-278)回傳 lambda: False

本機的 kv 其實已經初始化好了,但讀取問的是沒連上的 client,永遠得到 False。那行 assert 沒附訊息,所以使用者只看到 bare AssertionError。

哪一行 assert 炸掉,要看走哪條路:_record_stats 只在 not connect_only 時呼叫(node.py:481),也就是起新 cluster 的路徑。如果機器上已經有 cluster(log 會印 Connecting to existing Ray cluster),走的是 connect_only=True,炸掉的應該是另一個同樣寫法的 assert _internal_kv_initialized(),例如 services.py:657 或 usage_lib.py 裡的。實際是哪一行還沒驗證。

那為什麼不直接在連線失敗時把旗標關掉?

因為旗標是整個 process 共用的,而 connect 失敗的那個地方看不到其他 client 的狀態。要安全地關掉,得先知道下面這些情況:

  • 其他 context 還連著:用 allow_multiple=True 時可能有好幾個 client context。一個失敗就把旗標關掉,其他還連著的 context 的 ray.get / .remote 會全部改走本機路徑而壞掉(第 4 節 A)。_ClientContext 看不到 _all_contexts,只有 RayAPIStub 看得到,所以 disconnect / shutdown 都只在 len(_all_contexts) == 0 時才關。
  • 測試自己在管旗標:_inside_client_test 時,旗標由測試的 enable_client_mode() 控制,connect 不該去動它(第 4 節 B)。
  • RAY_CLIENT_MODE=1:整個 process 預設就是 client mode,關掉旗標會改變這個預設行為。
  • 旗標是刻意在連線之前打開的:連線過程中呼叫的 API 要走 client 路徑。

再加上 maintainer 的規格本來就是「連線失敗後本機 ray.init() 仍然要失敗,只是錯誤要清楚」,所以 PR #67407 不動旗標的生命週期,只在 ray.init() 開頭用 client_mode_should_convert() and num_connected_contexts() == 0 提早擋下,給出 Ray Client is already initialized。這樣既不會碰到上面那些情況,也不會讓使用者掉進「一半本機、一半 client」的狀態。

2. 旗標的生命週期

關鍵是分清楚「per-context」和「process-wide」兩層。旗標只有一個,context 可以有很多個。

位置動作條件
_ClientContext.connect __init__.py:159-162開啟not self._inside_client_test
_ClientContext.disconnect __init__.py:247不動旗標只關自己的 worker
RayAPIStub.disconnect __init__.py:373-374關閉len(_all_contexts) == 0
RayAPIStub.shutdown __init__.py:403-404關閉len(_all_contexts) == 0
enable_client_mode() client_mode_hook.py:77開 / 關測試用的 context manager
這次的修改 __init__.py:222關閉無條件

既有的兩個關閉點都會先檢查「還有沒有別的 context 連著」。這次的修改是唯一一個不檢查的。

3. 目前的修改

         except Exception:
             self.disconnect()
+            _explicitly_disable_client_mode()
             raise

對 issue 的情境(只有 default context、之前沒連過任何東西)是對的:失敗後旗標回到 False,下一個 ray.init() 走本機路徑。

但 issue 本身指的修改位置是 RayAPIStub.connect,不是 _ClientContext.connect。這個差別就是下面兩個問題的來源。

4. 隱式假設

A. 假設沒有其他 client context 連著(會壞掉 allow_multiple)

client_builder.py:175-184:allow_multiple=True 時,每次 connect 都會 set_context(None) 換一個新的 _ClientContext。

  1. context A 連線成功,旗標 = True,A 在 _all_contexts 裡。
  2. context B 連線失敗,走到第 222 行,旗標 = False。
  3. A 還連著,但所有 @client_mode_hook 函式現在都走本機路徑,A 的 ray.get / .remote 就壞了。

_ClientContext 看不到 _all_contexts,所以在這一層根本沒辦法判斷該不該關。這是要往上搬到 RayAPIStub 的原因。

B. 開關不對稱:_inside_client_test

開啟時,如果 _inside_client_test 為 True 就跳過,因為測試會自己用 enable_client_mode() 管理旗標。關閉時卻不看這個條件。在這種測試裡只要有一次 connect 失敗,測試的 client mode 就被偷偷關掉,後面的步驟行為會跑掉。

小問題(既有行為):如果 process 是用 RAY_CLIENT_MODE=1 啟動的(is_client_mode_enabled_by_default,client_mode_hook.py:20),connect 失敗也會把這個預設值關掉。disconnect 本來就會這樣,可以接受,在 PR 描述提一句就好。

5. 建議的改法

把第 222 行拿掉,改在 RayAPIStub.connect 處理,條件比照 disconnect:

python/ray/util/client/__init__.py · RayAPIStub.connect

def connect(self, *args, **kw_args):
    self.get_context()._inside_client_test = self._inside_client_test
    try:
        conn = self.get_context().connect(*args, **kw_args)
    except Exception:
        global _lock, _all_contexts
        with _lock:
            # 只有在沒有其他 client context 連著時,才撤銷
            # _explicitly_enable_client_mode()
            if not self._inside_client_test and len(_all_contexts) == 0:
                _explicitly_disable_client_mode()
        raise
    global _lock, _all_contexts
    with _lock:
        _all_contexts.add(self._cxt.handler)
    return conn

失敗的 context 從來沒被加進 _all_contexts,所以 len == 0 正好代表「這次失敗之前也沒有任何連線」。

副作用:_ClientContext.init 裡直接呼叫的 self.connect 失敗時就不會重設旗標。RayAPIStub.init 也可以加同樣的保護,看要不要一起做。

7. 測試的坑:from ... import 拿到的是快照

2026-10-24 寫回歸測試時踩到

第一版測試是這樣寫的:

from ray._private.client_mode_hook import is_client_mode_enabled
...
with pytest.raises(ConnectionError):
    ray.init(f"ray://127.0.0.1:{find_free_port()}")
assert not is_client_mode_enabled   # 永遠通過,修不修都一樣

為什麼永遠通過?

from X import name 不是「連到」X.name,而是在 import 當下把它指向的物件,綁到測試 module 自己的名字上。import 時旗標是 False,所以測試裡的 is_client_mode_enabled 就是一個固定的 False。

之後 _explicitly_enable_client_mode() 用 global is_client_mode_enabled 重新賦值(client_mode_hook.py:58-64),改的只是 client_mode_hook module 裡的那個名字。bool 是 immutable,兩個名字從此各指各的,測試那份不會跟著變。

from ray._private import client_mode_hook
from ray._private.client_mode_hook import (
    is_client_mode_enabled, _explicitly_enable_client_mode,
)

_explicitly_enable_client_mode()
print(is_client_mode_enabled)                   # False(快照)
print(client_mode_hook.is_client_mode_enabled)  # True(真正的旗標)

那為什麼測試是在下一行 assert ray.is_initialized() 才失敗?

旗標的 assert 是假通過,bug 其實還在。旗標卡在 True 時,ray.init() 照樣會開本機 cluster(init 只有在 RAY_CLIENT_MODE=1 時才會被轉走),但 ray.is_initialized() 有 @client_mode_hook(worker.py:2497),會被轉到沒連上的 Ray Client,所以回傳 False。

規則:會被 global 重新賦值的 module-level 變數,一律透過 module 讀:client_mode_hook.is_client_mode_enabled。Ray 自己的 client_mode_should_convert() 也是在 module 內部讀它。

檢查方式:把修正 revert 掉,回歸測試應該要在旗標那一行失敗。如果不會,這個 assert 就沒在測東西。
