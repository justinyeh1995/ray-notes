Issue 67142 Client Mode Reset

整理自 2026-10-18 的 review · 分支 fix/ray-init-client-mode · 行號以 master 95d3a43269 加上未 commit 的修改為準 · ray#67142

一句話:在 _ClientContext.connect 的 except 裡加 _explicitly_disable_client_mode(),可以修好 issue 的 repro,但寫法不安全。它把整個 process 共用的旗標無條件關掉,沒管其他 client context 是否還連著。

  • 問題 A(嚴重):用 allow_multiple=True 時,第二個 connect 失敗會把第一個還連著的 context 的 client mode 一起關掉。
  • 問題 B:開啟有 _inside_client_test 判斷,關閉卻沒有,兩邊不對稱。
  • 建議:改在 RayAPIStub.connect 處理,比照 disconnect,只在 len(_all_contexts) == 0 且不在 client test 時才關。
  • 驗證狀態:還沒跑過。這台機器的 Python 沒有安裝 Ray。

1. Issue 在講什麼

症狀是什麼?

ray.init("ray://...") 連線失敗之後,同一個 process 再呼叫本機的 ray.init() 會在 node.py 的 _record_stats 撞到 AssertionError,而不是正常啟動本機 cluster。

issue 附的 repro

import ray
import ray._private.client_mode_hook as hook
from ray._common.network_utils import find_free_port

try:
    # 這個 port 沒有任何東西在 listen
    ray.init(f"ray://127.0.0.1:{find_free_port()}")
except ConnectionError as e:
    print("ray:// connect failed:", type(e).__name__, e)
print("client mode enabled after failure:", hook.is_client_mode_enabled)  # True
ray.init()  # AssertionError

根因?

client_mode_hook.is_client_mode_enabled(client_mode_hook.py:16)是 module-level 的全域旗標,決定所有 @client_mode_hook 修飾的函式要走本機路徑還是 Ray Client 路徑。_ClientContext.connect 在連線之前就把它打開(__init__.py:162),失敗時只呼叫 per-context 的 self.disconnect(),而這個 disconnect 不會動到旗標。旗標就這樣一直停在 True。

Workaround:失敗後手動呼叫 ray.util.disconnect(),它走的是 RayAPIStub.disconnect,會把旗標關掉。

2. 旗標的生命週期

關鍵是分清楚「per-context」和「process-wide」兩層。旗標只有一個,context 可以有很多個。

位置動作條件
_ClientContext.connect __init__.py:159-162開啟not self._inside_client_test
_ClientContext.disconnect __init__.py:247不動旗標只關自己的 worker
RayAPIStub.disconnect __init__.py:373-374關閉len(_all_contexts) == 0
RayAPIStub.shutdown __init__.py:403-404關閉len(_all_contexts) == 0
enable_client_mode() client_mode_hook.py:77開 / 關測試用的 context manager
這次的修改 __init__.py:222關閉無條件

既有的兩個關閉點都會先檢查「還有沒有別的 context 連著」。這次的修改是唯一一個不檢查的。

3. 目前的修改

         except Exception:
             self.disconnect()
+            _explicitly_disable_client_mode()
             raise

對 issue 的情境(只有 default context、之前沒連過任何東西)是對的:失敗後旗標回到 False,下一個 ray.init() 走本機路徑。

但 issue 本身指的修改位置是 RayAPIStub.connect,不是 _ClientContext.connect。這個差別就是下面兩個問題的來源。

4. 隱式假設

A. 假設沒有其他 client context 連著(會壞掉 allow_multiple)

client_builder.py:175-184:allow_multiple=True 時,每次 connect 都會 set_context(None) 換一個新的 _ClientContext。

  1. context A 連線成功,旗標 = True,A 在 _all_contexts 裡。
  2. context B 連線失敗,走到第 222 行,旗標 = False。
  3. A 還連著,但所有 @client_mode_hook 函式現在都走本機路徑,A 的 ray.get / .remote 就壞了。

_ClientContext 看不到 _all_contexts,所以在這一層根本沒辦法判斷該不該關。這是要往上搬到 RayAPIStub 的原因。

B. 開關不對稱:_inside_client_test

開啟時,如果 _inside_client_test 為 True 就跳過,因為測試會自己用 enable_client_mode() 管理旗標。關閉時卻不看這個條件。在這種測試裡只要有一次 connect 失敗,測試的 client mode 就被偷偷關掉,後面的步驟行為會跑掉。

小問題(既有行為):如果 process 是用 RAY_CLIENT_MODE=1 啟動的(is_client_mode_enabled_by_default,client_mode_hook.py:20),connect 失敗也會把這個預設值關掉。disconnect 本來就會這樣,可以接受,在 PR 描述提一句就好。

5. 建議的改法

把第 222 行拿掉,改在 RayAPIStub.connect 處理,條件比照 disconnect:

python/ray/util/client/__init__.py · RayAPIStub.connect

def connect(self, *args, **kw_args):
    self.get_context()._inside_client_test = self._inside_client_test
    try:
        conn = self.get_context().connect(*args, **kw_args)
    except Exception:
        global _lock, _all_contexts
        with _lock:
            # 只有在沒有其他 client context 連著時,才撤銷
            # _explicitly_enable_client_mode()
            if not self._inside_client_test and len(_all_contexts) == 0:
                _explicitly_disable_client_mode()
        raise
    global _lock, _all_contexts
    with _lock:
        _all_contexts.add(self._cxt.handler)
    return conn

失敗的 context 從來沒被加進 _all_contexts,所以 len == 0 正好代表「這次失敗之前也沒有任何連線」。

副作用:_ClientContext.init 裡直接呼叫的 self.connect 失敗時就不會重設旗標。RayAPIStub.init 也可以加同樣的保護,看要不要一起做。
