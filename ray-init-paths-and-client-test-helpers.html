ray.init 路徑與 Client 測試工具

整理自 2026-10-26,寫 ray#67407 時的筆記 · 行號以 master ce4256ec64 加上 PR 的修改為準,之後可能會跑掉,用函式名稱找比較穩 · 相關筆記:Ray Client 模式關鍵路徑、Issue 67142 Client Mode Reset

一句話:ray.init() 先看 address 裡有沒有 ://。有的話,這個 process 會變成 Ray Client 的 client;沒有的話,這個 process 自己會變成 driver,然後才決定是連上現有的 cluster,還是自己起一個。

  • Client:真正的 driver 在 server 那一邊,本機只是 gRPC client,呼叫靠 @client_mode_hook 轉過去。
  • Driver:本機的 global_worker 直接連上 GCS 和 raylet。
  • ray_start_client_server:測試工具,把 client 和 server 放在同一個 process 裡。所以「process 裡有 client」不代表「這個 process 不能當 driver」。

1. ray.init 的分岔總覽

ray.init 在 python/ray/_private/worker.py。在讀 address 之前,@client_mode_hook 已經先做了一次判斷:

  1. Hook 這一層(client_mode_hook.py:126):只有在 RAY_CLIENT_MODE=1 時,init 本身才會被轉成 client 呼叫。其他情況下,不論旗標怎麼設,init 都會進到本機的函式。
  2. RAY_ADDRESS:如果 address 是 None 或 "auto",而且有設定環境變數 RAY_ADDRESS,就用它取代 address。所以 RAY_ADDRESS=ray://... 加上不帶參數的 ray.init(),一樣會走 client。
  3. 有沒有 ://(if address is not None and "://" in address):有就走 client builder,最後 return ctx;沒有就往下走本機路徑。
呼叫方式走哪條路結果
ray.init("ray://host:10001")Client連到 head 上的 client server。本機不是 driver。
ray.init("xxx://...")Clientclient_builder._get_builder_from_address 會 import xxx,改用那個 module 的 ClientBuilder。ray:// 只是其中一種。
ray.init("http://...")直接報錯ValueError。通常是把 dashboard 的位址誤設給了 RAY_ADDRESS。
ray.init()本機找得到現有的 cluster 就 connect,找不到就 start。見第 2 節。
ray.init("auto")本機一定要找到現有的 cluster,找不到就丟 ConnectionError。
ray.init("local")本機一定 start 一個新的,不管有沒有現有的 cluster。
ray.init("10.0.0.5:6379")本機以 driver 身份連到這個 GCS。這可能是遠端的 cluster:「本機路徑」不等於「本機的 cluster」。

幾個只在某一條路徑有效的參數:

  • allow_multiple=True:只有 client 能用。在本機路徑上會直接丟 RuntimeError。
  • ignore_reinit_error=True:兩條路都有。本機路徑上,如果 global_worker.connected 已經是 True,就回傳現有的 context,不會丟出「called ray.init twice」的錯誤。

2. 本機路徑:connect 還是 start

本機路徑呼叫 services.canonicalize_bootstrap_address(address, _temp_dir),裡面再呼叫 get_ray_address_from_environment(services.py:413):

address 是 None 或 "auto"?
├─ 有 RAY_ADDRESS → 用它
├─ 讀 /tmp/ray/ray_current_cluster(上一次成功 `ray start` 寫下的 GCS 位址)
│    └─ address 是 "auto" 而且這個檔案沒有 → 改用任何偵測到的 gcs_server process(舊行為)
├─ 找到位址 → "Connecting to existing Ray cluster at address: ..."
└─ 沒找到
     ├─ address 是 None   → 回傳 None → start 新的
     └─ address 是 "auto" → ConnectionError("Could not find any running Ray instance...")

address 是 "local" → 直接回傳 None → start 新的
其他 address → parse 成 host:port → connect

回傳 None 之後,程式會走到 if bootstrap_address is None:(註解寫的是 we need to start a new cluster),在這個 process 裡起 GCS 和 raylet,然後印出 Started a local Ray instance。

注意:ray_current_cluster 只記錄最後一次寫入的位址。會寫入的只有 ray start(scripts.py)和測試用的 cluster_utils.Cluster;自己 ray.init() 起的 cluster 不會寫進這個檔案。如果機器上同時有好幾個 cluster,ray.init() 會挑檔案裡的那一個,並印出 Found multiple active Ray instances 的警告。

3. 誰才是 driver

driver 是「以 SCRIPT_MODE 連進 cluster、負責提交 task 的 process」。worker.py 的 global_worker 是 module 層級的全域物件,一個 process 只有一份,上面記錄著這個 process 是不是 driver、有沒有連上。

情境你的 script processdriver 在哪
本機 ray.init(),start 新的driver,同時也是 head 的擁有者你的 process
本機 ray.init(),connect 現有的driver你的 process
ray.init("ray://..."),server 是用 ray start 起的gRPC client,global_worker.connected 是 Falsehead 上另外起的 SpecificServer process。proxier 會為每個 client 起一個(proxier.py 的 start_specific_server)。
ray_start_client_server()(測試)同時是 client 和 server同一個 process:server 在 disable_client_hook() 裡呼叫本機的 ray.init()。

在 client 模式下,本機沒有 driver,所以 ray.get、.remote() 不能在本機執行,只能靠 hook 經由 gRPC 轉給遠端的 driver。這就是 @client_mode_hook 存在的原因。

4. Process 裡的三個狀態

狀態位置範圍意思
global_worker.connectedworker.py整個 process這個 process 是不是已經以 driver 或 worker 的身份連上了
is_client_mode_enabledclient_mode_hook.py 的 module 全域變數整個 process有人明確開啟過 client mode
hook statusclient_mode_hook.py 的 threading.local()每個 thread 各一份這個 thread 現在要不要轉呼叫。disable_client_hook() 會把它關掉。

判斷「這次呼叫要不要轉成 client 呼叫」的是 client_mode_should_convert():

(is_client_mode_enabled or is_client_mode_enabled_by_default)   # RAY_CLIENT_MODE=1
    and _get_client_hook_status_on_thread()

只看旗標,不看 hook status,就會漏掉「同一個 process 裡,server 那一邊合法地呼叫本機 init」的情況。第 6 節就是這樣出錯的。

旗標什麼時候會被打開:

  • ray.init("ray://...") → client_connect.connect 會無條件呼叫 _explicitly_enable_client_mode()(client_connect.py:55),而且是在連線之前。連線失敗之後沒有人把它關掉,這就是 #67142。
  • 低階的 ray.util.client.ray.connect() → _ClientContext.connect 只有在 not self._inside_client_test 時才打開(util/client/__init__.py:159)。

旗標什麼時候會被關掉:ray.util.disconnect() 或 ray.shutdown(),而且只有在所有 client context 都斷開(len(_all_contexts) == 0)時才會關。

5. ray_start_client_server 家族

這些 helper 都在 python/ray/util/client/ray_client_helpers.py,用途是在測試裡不用 ray start,直接在同一個 process 裡起一個 Ray Client server(port 固定是 50051),再讓 client 連上去。這樣比較快,也比較容易 debug。

┌──────────── 同一個 pytest process ────────────┐
│                                               │
│  test code (main thread)                      │
│    └─ ray.util.client.ray  ── gRPC ──┐        │
│                                      ▼        │
│  client server(gRPC threads, port 50051)     │
│    └─ with disable_client_hook():             │
│          ray.init(...)   ← 真正的 driver       │
│                                               │
└───────────────────────────────────────────────┘
Helper做什麼server 端怎麼 init
ray_start_client_server_pair()本體。設定 ray._inside_client_test = True,呼叫 ray_client_server.serve(..., 50051),再 ray.connect(...)。yield 出 (client, server)。預設的 handler(server.py 的 serve 裡):with disable_client_hook(): ray.init(...),也就是起一個新的本機 cluster
ray_start_client_server()包一層 pair,只 yield client。最常用。同上
ray_start_client_server_for_address(address)同上,但 server 會連到你給的 cluster。test_client.py 用它搭配 call_ray_start_shared,讓很多測試共用同一個 head,省下每次起 cluster 的時間。with disable_client_hook(): ray.init(address, ...)
ray_start_cluster_client_server_pair(address)舊的寫法,類似 for_address。handler 直接 real_ray.init(address=address)。server 本身的 Init 處理已經包在 disable_client_hook() 裡了。

結束時,helper 會呼叫 ray.disconnect() 和 server.stop(0),然後在 disable_client_hook() 裡等 ray.is_initialized() 變成 False,最多等 30 秒。

跟 call_ray_start 的差別

ray_start_client_servercall_ray_start(帶 client server port)
server 在哪pytest 自己的 process 裡另一個 process(ray start --head)
driver 在哪pytest 自己的 processhead 上的 SpecificServer process
port固定 50051自己指定,例如 --ray-client-server-port 25307
client 旗標helper 的 ray.connect 不會打開(因為 _inside_client_test);但測試裡如果自己呼叫 ray.init("ray://localhost:50051"),就會打開ray.init("ray://...") 會打開
結束時disconnect 並停掉 serverray.shutdown() 加上 ray stop,會停掉這台機器上所有的 Ray

用到這些 helper 的檔案(2026-10-26 時的搜尋結果):test_client.py、test_client_references.py、test_ray_init_2.py、test_dataclient_disconnect.py、test_client_terminate.py、test_client_metadata.py、test_generators.py、test_client_warnings.py、test_ray_init.py、test_client_init.py、test_client_builder.py,另外還有 tune、rllib、horovod、ludwig 的 client 測試,以及 ray_client_microbenchmark.py。

6. PR #67407 學到的事:原始旗標不夠用

第一版的檢查放在本機路徑的開頭:

if ray._private.client_mode_hook.is_client_mode_enabled:
    raise RuntimeError("Ray Client is already initialized in this process. ...")

CI 的 test_ray_init_2.py::test_env_var_no_override(本機的 test_ray_init_valid_keyword_with_client 也一樣)失敗了:

Call to `ray.init()` on the server failed with: Ray Client is already initialized in this process. ...

過程是這樣的:

  1. ray_start_client_server() 在同一個 process 裡起 server,然後 given_connection.disconnect()。
  2. 測試接著呼叫 ray.init("ray://localhost:50051"),而 client_connect.py:55 會無條件把旗標設成 True。
  3. server 收到 Init,在 disable_client_hook() 裡呼叫本機的 ray.init()。這個呼叫是合法的,卻被原始旗標的檢查擋了下來。

改成 client_mode_should_convert() 之後,server 那個 thread 的 hook status 是 False,所以不會被擋;測試主 thread 的本機 ray.init() 照樣會被擋。這個條件剛好就是「Node(...) 裡的 hook 呼叫會不會被誤轉」,也就是 #67142 出問題的條件。

通則:想問「這次呼叫會不會被轉成 client 呼叫」,用 client_mode_should_convert()。is_client_mode_enabled 只回答「有沒有人開過 client mode」,不知道現在是哪個 thread、hook 有沒有被關掉。

另外,要讀 module 的全域變數,要用完整路徑或者讀 module 的屬性,不要 from ... import is_client_mode_enabled,那樣只會複製到 import 當下的值。import 函式就沒有這個問題。

7. 測試 fixture 速查

Fixture做什麼什麼時候用
shutdown_only不起任何東西,只在結束時 ray.shutdown()測試自己呼叫 ray.init(),或者根本不需要 cluster(例如連線失敗的情境)
call_ray_start在另一個 process 執行 ray start ...,結束時 ray.shutdown() 再 ray stop需要一個真的 head,例如要連 ray:// 的 client server
ray_start_regular 等在測試的 process 裡 ray.init(...)一般的 driver 測試

傳指令給 call_ray_start

@pytest.mark.parametrize(
    "call_ray_start",                       # 名字要跟 fixture 一樣
    ["ray start --head --ray-client-server-port 25307 --port 0"],
    indirect=True,                          # 值交給 fixture(request.param),不是給測試函式
)
def test_xxx(call_ray_start):
    ray.init("ray://localhost:25307")
  • indirect=True:沒有它的話,pytest 會把字串直接當成參數傳給測試,取代 fixture,結果就不會起 cluster。
  • --port 0:GCS 的 port 讓系統自己挑,避免跟 6379 撞到。測試是透過 client server 連線的,不會直接碰 GCS。
  • client server port 要寫死:測試要事先知道連哪個 port。挑一個沒人用的,不要用預設的 10001,也不要跟同一個檔案裡其他測試的 port 一樣。可以先用 grep -rl <port> python/ray/tests 確認。
  • 本機跑 call_ray_start 的測試之前:teardown 的 ray stop 會把你自己的 dev cluster 也停掉。
  • in-process server 的測試不要平行跑:它們都用 50051,會互相搶 port。

fixture 內部(python/ray/tests/conftest.py:828、:845)

  • 拿參數:getattr(request, "param", default_cmd)。沒有 parametrize 就用預設的 ray start --head --num-cpus=1 --min-worker-port=0 --max-worker-port=0 --port 0。
  • 也可以傳 dict:{"cmd": "...", "env": {...}},env 會合併到 os.environ 再交給 subprocess,用來替 head 設環境變數。
  • yield 的值:從 ray start 的輸出解析 --address='...',得到 GCS address。連 ray:// 的測試通常用不到這個值,參數擺在那裡只是為了觸發 fixture 起 cluster。

PR #67407 的兩個例子

  • test_ray_init.py 用 25307,test_client_multi.py 用 25308(test_multi_client_connect_after_client_connect_failed:先連一個沒人聽的 port 拿到 ConnectionError,再用 allow_multiple=True 連 25308 跑 task)。兩個檔案的 port 分開,同時跑時才不會撞到。
  • 這類測試要用 call_ray_start 而不是 ray_start_client_server,因為 client server 必須在另一個 process,test process 才是純 client,跟使用者的真實情境一樣。原因見第 6 節。

8. 複習題

ray.init() 沒有給參數,機器上有一個用 ray start --head 起的 cluster。會發生什麼事?

走本機路徑。/tmp/ray/ray_current_cluster 裡有那個 cluster 的 GCS 位址,所以會 connect 上去,印出 Connecting to existing Ray cluster。你的 process 會以 driver 身份連進去。

ray.init("10.0.0.5:6379") 會走 client 還是本機路徑?

本機路徑,因為 address 裡沒有 ://。你的 process 會以 driver 身份直接連到那個遠端的 GCS。「本機路徑」指的是「這個 process 要成為 driver」,不是「連本機的 cluster」。

ray.init("ray://...") 連線成功之後,driver 在哪裡?

在 server 那一邊。用 ray start 起的 client server(proxier)會為每個 client 另外起一個 SpecificServer process,由它當 driver。你的 process 只是 gRPC client,global_worker.connected 是 False。

ray:// 連線失敗之後,為什麼本機的 ray.init() 會在 Node(...) 裡出現空的 AssertionError?

client_connect.connect 在連線之前就把旗標打開了,失敗後沒有關掉。本機的 init 本身不會被轉(hook 對 init 有例外),但它裡面呼叫的 _internal_kv_initialized 有 @client_mode_hook,會被轉到一個沒連上的 client,回傳 False,於是 assert 失敗。

為什麼 ray_start_client_server() 的 server 可以在「client 已經存在」的 process 裡呼叫本機 ray.init()?

server 是在 disable_client_hook() 裡呼叫的。這會把那個 thread 的 hook status 設成 False,所以 client_mode_should_convert() 是 False,所有呼叫都走本機。旗標是整個 process 共用的,但 hook status 是每個 thread 各一份。

想在本機路徑上擋掉「這個 process 其實在 client 模式」的情況,要檢查什麼?

client_mode_should_convert()。只看 is_client_mode_enabled 會誤擋 in-process server 那個合法的 init(見第 6 節)。

@pytest.mark.parametrize("call_ray_start", [...], indirect=True) 少了 indirect=True 會怎樣?

字串會直接當成測試參數 call_ray_start 傳進去,取代 fixture,所以根本不會執行 ray start。接著 ray.init("ray://...") 會等大約 30 秒的連線 timeout,然後失敗。

連到一個沒有人聽的 ray:// port,要多久才會失敗?

大約 30 秒。connection_retries=3 加上 backoff,最後丟出 ConnectionError: ray client connection timeout。ray.init("ray://...") 沒辦法調整 retries,所以測試這個情境時,要把這 30 秒算進去。
